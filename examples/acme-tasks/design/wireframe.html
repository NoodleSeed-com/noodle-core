How to read these wireframes

Solid-border phones are the in-ChatGPT app. Acme Tasks is a two-way (read + write) app, not a discovery funnel: every widget reflects the user's real list, and each action — capture, re-prioritize, complete — is recorded through a tool call and confirmed in-chat. The single dashed phone is the one-time account link (customerAuth); there is no transactional off-app step.

Widgets are built with the Noodle Seed authoring SDK — tool + view renders TaskList; tool + app visibility powers the in-widget re-prioritize. Styling uses host/Noodle Seed semantic tokens via CSS cascade layers; the brand accent (#7C3AED) is reserved for the logo, checks, primary CTA and high emphasis. Priority uses fixed semantic colors: high red · medium amber · low slate.

First-run

Connect Acme Tasks — scoped, once

Because the app writes to the user's tasks, the very first interaction is a scoped account connection. It names exactly what the app can read and change, is dismissed forever after, and the original request resumes automatically. (This flagship seeds the list so the flows stay in focus; the connect screen is the production pattern — see customer-auth.)

Why it's built this way

TRUST An app that can complete and re-prioritize your tasks needs unambiguous, plain-language consent — the scope card names read vs. write in the user's words and links the revoke path, rather than burying it in an OAuth redirect.

ACME Uses Noodle Seed's customerAuth end-user OAuth. One connection powers all three flows; the delegated credential is held by the credential broker, never surfaced to the model, the widget, or logs.

Flow 1 · lowest friction

Capture — a spoken thought becomes a task, instantly

The moment a task is mentioned it lands on the list. The model parses the prose into a title and priority, the row appears optimistically, and add_task records it — no form, no app-switch.

Why it's built this way

UX Capture must be the fastest path in the app — the thought is fragile. "Add X, high" is one turn: the model fills { title, priority } from natural language, so the user never fills a field by hand.

UI The new row renders immediately (optimistic), then the tool call confirms with a spoken-ready status. The capture input lives at the top of TaskList so keyboard capture and voice capture converge on the same widget.

TRUST Priority is the user's: the model may suggest ("sounds high?") but sets what the user says, and defaults to medium when unstated — it never silently ranks work.

Flow 2 · the hub

Prioritize — read the day, then re-order it in place

list_today renders the grounded list, highest priority first; the per-row priority control (a tool + app visibility helper hidden from the model) lets the user re-rank without describing the task twice. This is the widget the other two flows write into.

Why it's built this way

UX "What's on my plate?" wants an answer and a next move. The list is grouped high → low so the triager sees the real order at a glance and adjusts with one tap.

ACME Re-prioritize is set_priority as tool + app visibility — widget-only, hidden from the model's tool surface. The model reasons about three tools (list, add, complete); the fourth is pure UI plumbing, keeping the model's choices clean.

TRUST The list only ever shows tasks that exist — the app never invents a task or a priority. Every re-rank echoes a confirmation ("Set review_pr to high priority").

Flow 3 · the payoff

Complete — check it off by voice or tap, confirmed every time

The satisfaction loop. The user finishes work and closes it out — either by tapping the row's check or by saying "mark X done" (complete_task is model-visible). The row strikes through, the open count drops, and the model narrates what changed.

Why it's built this way

UX Completion is the reward that drives return visits, so it is friction-free two ways: the check in TaskList and the spoken "mark X done". Ending on an all-clear empty state nudges the next capture instead of a dead end.

TRUST Completion is never silent: complete_task returns "Completed '…'" plus the remaining count, and the struck-through row is the visible receipt. The model confirms in the same turn.

ACME complete_task is model-visible (unlike re-prioritize) precisely because "I finished X" is a natural sentence the user will say — the model must be able to act on it directly.

Technical appendix

MCP tools & call sequence

The four tools behind the flows. list_today is the only widget-opening tool (tool + view); set_priority is widget-only (tool + app visibility, hidden from the model); add_task and complete_task are model-visible.

Read & render (Flow 2 · the hub)

READlist_today — returns { status, focus, tasks:[{ id, title, priority, done }] } and renders TaskList
Input { focus:"today" }. Read-only annotation; host status copy: invoking "Loading your tasks…", invoked "Tasks ready". This is the single widget-opening tool — the other flows write into the card it renders.

Capture (Flow 1)

WRITEadd_task — returns { status, title, priority }
Input { title, priority: "high"|"medium"|"low" = "medium" }. Model-fillable from prose ("book flights, low" → { title, priority:"low" }); local non-destructive write. Status is spoken-ready so the model confirms in one turn.

Prioritize (Flow 2 helper) & Complete (Flow 3)

WRITEset_priority — returns { status, task, priority } · tool + app visibility, hidden from the model
Input { task:id, priority }. Called only by the priority ▾ in TaskList — keeps the model's tool surface to the three it should reason about.
WRITEcomplete_task — returns { status, task } · model-visible
Input { task:id, title:"" }. Model-visible so "I finished X" completes directly; local non-destructive write, confirmed with the remaining count.
